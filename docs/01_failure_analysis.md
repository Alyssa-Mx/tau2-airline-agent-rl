# 01 · 失败归因：先搞清楚模型是怎么失败的

> **一句话**：原模型的失败里，**2/3 不是答错，而是对话在 40 步处被截断**；截断的对话里约 **三成其实活已经干完**，只是没在步数内收尾。官方 0/1 判分把"做对了没收尾"、"做错了"、"跑飞了"压成同一个 0，这就是后面奖励设计的出发点。

复现：`python analysis/reproduce.py failure`

---

## 1. 闭环仿真是怎么判分的

```
User Task ──► User Simulator (DeepSeek-v4-Flash, temp 0)
                   ▲    │ 自然语言
                   │    ▼
              Agent (Qwen3.5-4B) ──工具调用──► Tool Environment（航空公司数据库，14 个工具，真实读写）
                                                     │
                     对话结束 ──► Evaluator：数据库终态 == gold？ × 该告诉用户的信息说到了没有？
```

- 每道题给用户模拟器一个带目的的剧本（"你想改签，但不想付钱……"），客服要按 `policy.md` 调工具完成或拒绝。
- **单条对话的分 = DB × COMMUNICATE**（τ²-bench airline 官方 `reward_basis`，本仓库称"宽松口径"）。另附"严格口径"= 再乘 ACTION（gold 动作全部按参数调用过）。
- **结束原因不是 `user_stop` / `agent_stop`（例如撞 40 步）→ 直接记 0**，不管中间做了什么。这一条是整条线的起点。

## 2. 400 条轨迹按"怎么死的"数一遍

对象：原模型（Qwen3.5-4B，不训练）在 20 道 held-out 测试题 × 20 遍 = **400 段对话**，旧口径引擎（见 [05_eval_protocol.md](05_eval_protocol.md)）。

| | 条数 | 占全部 | 占失败 |
|---|---:|---:|---:|
| 通过 | 295 | 73.8% | — |
| **撞 40 步被截断** | **70** | 17.5% | **66.7%** |
| 　其中伴随整轮 `"!!!!"` 刷屏 | 53 | 13.2% | |
| 　其中无刷屏 | 17 | 4.2% | |
| 正常结束但数据库终态错 | 35 | 8.8% | 33.3% |
| 正常结束但该说的没说（COMMUNICATE 错） | 0 | 0 | 0 |

- **撞步是最大失分源**，而且与"对话变长"是同一件事：所有 4B 配置里，通过的对话约 11 个客服轮，失败的 16–18 个；DeepSeek 通过 / 失败的对话长度几乎一样（9.6 vs 9.2）—— 它失败时是"一步走错"，4B 失败时是"拖死"。
- "该说的没说"在评测里是 0 条：20 道测试题里只有 1 道有沟通要求。**改 DB × COMM 的乘法形状收益极小**，这条候选被排除。
- 刷屏的真正原因是推理引擎的长上下文数值故障，不是模型退化，见 [03_context_harness.md §4](03_context_harness.md#4-刷屏的根因推理引擎而不是模型)。

## 3. 关键一步：把截断的对话"放它收尾"再判一次

做法：用 **tau2 自己的判分器**，把每条截断对话的结束原因改记成 `user_stop`，重新判 DB × COMMUNICATE —— 问的是"如果允许它收尾，它本来能不能过"。（`tools/export_data.py` 的 `regrade()`，结果在 `data/episodes.csv` 的 `regrade_pass` 列。）

| 截断的对话 | 条数 | 重判能过 | 说明 |
|---|---:|---:|---|
| **写库题**（gold 含写工具） | 31 | 5 | 能过的 5 条全部伴随刷屏 —— 不是"差一步收尾"，是已经跑飞了 |
| **只读题**（gold 只有查询） | 18 | **16** | 16 条 gold 查询全做了、多数没刷屏 —— **活干完了，只是没收尾** |
| **无 gold 动作**（应拒绝） | 21 | 13 | 13 条里 12 条是刷屏对话；数据库本来就不该改，"判对"不代表干了活 |

- gold 动作（名字 + 参数）已全部执行的：**22 / 70 = 31%**。
- 写库 + 只读题里重判能过的：**21 / 70 = 30%**。

一个典型例子（[`data/examples/truncated_but_done_task6.json`](../data/examples/truncated_but_done_task6.json)）：用户想给已订的票补买保险；政策不允许。客服查了预订（唯一的 gold 动作）、正确拒绝，但用户"绝不接受转人工"并反复追问，客服就反复转人工 —— 40 步用完，**0 分**。它和"把保险加上了"（违规）拿到的是同一个分。

## 4. 这张表给出了三个不同的答案

原来它们都被记成同一个 0：

| 情况 | 该怎么对待 | 依据 |
|---|---|---|
| 只读题：查完、说对、没收尾 | **应该给分** | 16/18 重判能过，gold 查询都做了 |
| 写库题：截断时库恰好是对的 | 给一点，把"做完没收尾"和"根本没做对"分开 | 很少（5/31），且都伴随刷屏 |
| 无 gold 题：库没被改 | **不给分** | 没有"干了活"的正面证据，几乎全是跑飞的对话 |

> **0/1 的结果奖励对这三种情况给出完全相同的梯度**。GRPO 的优势是组内相对量：一组 6 条全 0 就没有梯度 —— 模型学不到"在有限步数内收尾"，因为在它的经验里"收尾"和"做对"从来没被分开过。

→ 奖励设计见 [02_reward_design.md](02_reward_design.md)。另一半原因（上下文变长 → 推理故障 → 对话被拖死）见 [03_context_harness.md](03_context_harness.md)。

## 5. 一个被排除的方向：过程奖励

在做部分分之前，试过"写库 gold 动作召回率"作为过程分（只在全错组起作用；这组实验的原始数据没有收进本仓库）。离线 AUC 看起来不错（0.86），但上线后：
- 正常结束时它与数据库判定几乎重合（DB=1 的 258 条里 253 条 s=1）—— 没有额外信息；
- 它唯一起作用的地方（全错组）里，拿到正优势的对话 43–63% 是被截断 / 跑飞的 —— **方向与"做对题"不一致**；
- 在梯度里只占 0.7–7.4%，评测无可测差异。

教训：**过程分上线前，要在真实轨迹上看"谁拿到了正优势"，不能只看它和成功率的 AUC**。这也是为什么部分分奖励要先按"怎么结束的 + 题型"分类，而不是再设计一个连续分数。
