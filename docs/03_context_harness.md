# 03 · Agent Harness & Context Engineering（零训练）

> **一句话**：一个权重都不动，只改客服模型每次调用时"看到的上下文"和调用方式：每轮固定 prompt **5,040 → 3,208 token（−36.3%）**，其中工具 schema **3,242 → 1,410（−56.5%）**；配合 Qwen3.5 原生思考后，同一台推理服务上测试集 pass@1 **0.750 → 0.825**，截断率 **18.8% → 6.2%**，与 DeepSeek-v4-Flash 自己扮演客服 + 顾客的 **0.875** 在统计上分不出高低。
>
> 同时查清了一件事：原来的"长对话就崩"主要不是模型能力问题，而是**推理引擎在长 prompt 上的数值故障** —— 精简的一部分价值，是把 prompt 压到了故障门槛以下。

复现：`python analysis/reproduce.py harness` · 代码：[`harness/`](../harness)

---

## 1. 为什么要精简：token 账

用 Qwen3.5-4B 分词器量原模型 400 段对话的 4,756 次调用（`data/prompt_budget.json`）：

| 每次调用都要付的固定开销 | token |
|---|---:|
| 14 个工具的完整 JSON schema | **3,242**（其中 `book_reservation` 一个就 1,118） |
| 政策 `policy.md` 全文 | 1,690 |
| 通用指令 + 模板 | 108 |
| **合计** | **5,040** |

对话里还在逐轮增长：最贵的工具返回是 `get_reservation_details`（调了 994 次、每次约 320 token，总量第一）和 `search_onestop_flight`（每次平均 1,838、最大 3,300）。出现过刷屏的对话，平均工具返回 3,878 token，没刷屏的 1,372。

三个约束同时指向"把每次调用压短"：
1. **刷屏门槛**：单次调用 prompt 在 9,651 token 以下从没出现过整轮 `"!!!!"`，14k 以上 222/296 次调用刷屏（§4）；
2. **固定开销**占掉门槛的一半，对话还没开始；
3. 往 4B 的 system prompt 里多塞东西，分数单调下降（另一组实验：7.7KB → 0.750、14KB → 0.653、18.7KB → 0.413）。

## 2. 四项精简

代码：[`harness/lean_agent.py`](../harness/lean_agent.py)（tau2 `LLMAgent` 子类）。判分、题库、用户模拟器、步数上限全不变，tau2 轨迹里记录的仍是原始工具返回。

### ① 工具渐进式披露：写库工具只给存根，真要调用的那一刻才展开

**不能直接删参数 schema**：vLLM 的工具解析器按请求里的 schema 查每个参数的类型；没有 schema 一律当字符串 → `flights`、`passengers` 这类嵌套参数会变成字符串，tau2 执行时直接报错。所以做成两段式：

- 请求里的 `tools=` **始终是完整定义**（解析器一直有类型），只改模型看到的渲染：复制官方 chat template 加一个 `expanded_tools` 分支（[`chat_template_lean.jinja`](../harness/chat_template_lean.jinja)），**不传这个参数时与官方模板逐 token 相同**（40/40 条真实对话、思考开 / 关都验过）—— 所以原始组和精简组可以共用同一台推理服务，不引入实例差异。
- 8 个读工具保留完整定义，6 个写库工具只渲染"名字 + 一句描述"：

```text
完整定义（920 token）：
{"type":"function","function":{"name":"book_reservation","description":"Book a reservation.",
 "parameters":{"$defs":{"FlightInfo":{...},"Passenger":{...},"Payment":{...}},"properties":{"user_id":{...},
 "origin":{...},"destination":{...},"flight_type":{...},"cabin":{...},"flights":{...},"passengers":{...},
 "payment_methods":{...},"total_baggages":{...},"nonfree_baggages":{...},"insurance":{...}},"required":[...]}}}

存根（35 token）：
{"type":"function","function":{"name":"book_reservation",
 "description":"Book a reservation. (Parameters are shown when you call this tool.)"}}
```

- 模型调了一个只有存根的工具 → 包装层**丢弃这次生成**（不进状态、不进轨迹、不占 40 步），展开它后重新生成。50 题 × 4 遍里共展开 210 次，全部成功。展开集合每轮重置，历史里永远是存根。
- **固定开销 5,040 → 3,208，每次调用省 1,832 token；工具 schema 3,242 → 1,410。** 展开那一轮加回：订票 881、改航班 375、改乘客 236、改行李 207、发券 86、取消 47。
- 为什么不把读工具也存根（能到 2,642）：读工具的参数说明里有日期格式这类东西，风险高于收益。

### ② 工具返回无损压缩

进入 agent 状态前改写（`compact_result`）：航班搜索每班一行，其余去掉 JSON 的引号和空字段。**是格式压缩，不是摘要，没有模型参与。**

```text
search_direct_flight：509 token → 182 token（−64%）
原文：[{"flight_number": "HAT033", "origin": "JFK", "destination": "DTW", "status": "available",
       "scheduled_departure_time_est": "00:00:00", "scheduled_arrival_time_est": "02:00:00",
       "date": null, "available_seats": {"basic_economy": 5, "economy": 5, "business": 4},
       "prices": {"basic_economy": 88, "economy": 135, "business": 363}}, …]
紧凑：HAT033 JFK>DTW 00:00-02:00 basic_economy:5@$88 economy:5@$135 business:4@$363
```

| 工具（400 段对话合计） | 次数 | 原文 token | 紧凑 token | 省 |
|---|---:|---:|---:|---:|
| get_reservation_details | 994 | 319,678 | 261,964 | 18% |
| search_onestop_flight | 130 | 238,947 | 98,875 | **59%** |
| get_user_details | 342 | 121,839 | 103,377 | 15% |
| search_direct_flight | 287 | 61,952 | 22,393 | **64%** |

省得最狠的是航班搜索，但总量最大的预订详情本来就是紧凑键值，只省 18% —— 这一项的价值主要在削 90 分位。

### ③ 历史对象只保留最新状态

发给模型前（不改状态、不改轨迹）：除了最近 2 条、以及**每个预订号 / 用户号 / 航线+日期各自最近一次**的返回之外，其余工具返回换成 14 token 的占位 `[older get_reservation_details result omitted; call it again if needed]`。

这一项是踩坑迭代出来的：航班搜索的返回既没有预订号也没有用户号，最初两条新返回一进来就被换掉 —— 而用户正是从那次搜索里选的航班，后面订票要照抄航班号。修法是按"工具 + 航线 + 日期"钉住最近一次搜索。换占位以后模型**没有**反复重查（同参数的重复读调用：原模型 3 次、精简 2 次）。

### ④ 历史里的刷屏回复换占位

整轮 `"!!!!"` 的回复换成 `(previous reply was garbled and not delivered)`（256 → 9 token）。它阻止不了第一次刷屏，但能打断"刷一次就停不下来"。

### 回放估算：四项叠加对调用长度的作用

对原模型 400 段对话的 4,756 次调用逐项扣掉能省的 token（轨迹不变）：

| 叠加到 | 调用 token 中位数 | 90 分位 | ≥ 9,600 的调用 | 整段都低于 9,600 的对话 |
|---|---:|---:|---:|---:|
| 原始 | 6,995 | 13,026 | 1,069 | 197 / 400 |
| + ① 工具存根 | 5,165 | 11,271 | 720 | 278 |
| + ② 返回压缩 | 4,948 | 9,731 | 498 | 315 |
| + ③ 旧返回占位 | 4,948 | 9,345 | 434 | 323 |
| + ④ 刷屏占位 | 4,830 | 7,794 | **113** | **357** |

实测定版：2,534 个客服轮的 prompt 下限 3,208 / 中位 4,805 / 90 分位 7,240 / 最大 11,443，每段对话峰值 prompt 的中位数 10,551 → 6,756。

## 3. 让思考模式真正可用：三处修复

只做精简**不涨分**（§5），要配合思考。但 Qwen3.5 的原生思考在 vLLM 0.19.1 + tau2 上直接开会出问题，定版之前修了三处：

| 现象 | 根因（逐个探针查出来的） | 修法 | 效果 |
|---|---|---|---|
| 思考和回复抢同一个 2,048 上限 | 旧口径每轮上限是思考 + 回复共用；拆开数：回复部分最长只有 728 token，撞上限的全是思考 | 思考额度 4,096（`thinking_token_budget`）+ 回复 2,048 | 思考不再把回复挤掉 |
| 约 13% 的思考轮返回空回复，tau2 整段重开对话 | 模型没写 `</think>` 就 EOS，其中一部分把 `<tool_call>` 写在了思考里；vLLM 的 qwen3 解析器此时把整段当思考 → 正文为空 | 回移上游 vLLM PR #35687：思考里写出的 `<tool_call>` 视为思考结束（[插件](../harness/qwen3_toolend_reasoning_parser.py)） | 空回复 13.3% → 7.0% |
| 剩下的空回复"只写了打算就结束" | 同上，没有工具调用可救 | 用它自己的思考补上 `</think>`，在同一轮续写（`continue_final_message`，不重新采样） | 探针 15/15 成功、14/15 与思考里的打算一致；定版评测 **164/164** |

- 定版这一轮是干净的测量：**tau2 整段重开 0 次、infrastructure error 0 次、刷屏 0**。前一版只用"原样重采 ×3"兜底时，重采 578 次仍有 75 次空回复、tau2 重开 73 次 —— 失败的对话被重开后不计分，分数（0.838）有选择偏差，所以没有采用。
- 续写会不会让模型编造操作结果？专门查了"声称已取消 / 改签 / 预订成功、但此前没调过写工具"的回复：84 条续写里 1 条，且是在复述已有预订，不是捏造操作。
- 撤回过的方案："关掉思考重答"—— 调研业界没有采用者，还会把两种模式混进同一个分数。

## 4. 刷屏的根因：推理引擎，而不是模型

原模型 400 段对话里 102 段出现过整轮 `"!!!!"`（token id 0 刷满一轮）。按那次调用的 prompt 长度分段：9,600 以下 0 次；9.6–11k 9/209；11–12k 32/115；12–14k 87/178；14k 以上 222/296。

**决定性实验**：同一条真实对话截成不同长度，每个长度生成 12 次（`data/flood_probe.json`）：

| prompt token | vLLM 旧口径采样 | vLLM 原生采样（presence 1.5 + 重复检测） |
|---:|---:|---:|
| 5,031 / 6,130 / 8,465 | 0/12 / 0/12 / 0/12 | 0/12 / 0/12 / 0/12 |
| 12,677 | 6/12 | 7/12 |
| 14,784 | 4/12 | 7/12 |
| 17,509 | 10/12 | 6/12 |

| 对照（均为 Qwen3.5-4B） | 结果 | 结论 |
|---|---|---|
| **同一份权重用 HF transformers 跑，prompt 22,353 token** | **0/12** | 不是模型的长上下文退化 |
| 两种采样参数（上表两列） | 曲线重合 | 不是采样问题；重复抑制只是把坏输出截短 |
| 前缀缓存 | 出现刷屏的那几台服务本来就是关的 | 不是缓存污染 |
| **`--max-num-batched-tokens 32768`（整段 prompt 一次预填），17,509 token** | **0/12**（默认 8,192 分块预填：**12/12**） | **病根在分块预填**：Qwen3.5 的 Gated DeltaNet 线性注意力层，循环状态在预填块之间传递时出错 |

（另在 Qwen3.5-0.8B 上试过 SSM 状态 fp32、关 CUDA graph、单序列调度，都无效；但 0.8B 在 5.1k、未分块时就会刷屏，不分块预填对它也无效 —— 是另一条故障路径，这几条不作为 4B 的证据。）

这条定位把历史数据全解释通了：定版的峰值 prompt 中位 6,756 → 刷屏 0%；原始 prompt 的中位 9,955–10,551、尾部过 12k → 刷屏对话 25–32.5%。

**所以因果链要这样写**：精简降低刷屏 ≠ "上下文短了模型更稳"，而是"把 prompt 压到了引擎故障门槛以下"。旧口径 2×2 里精简的效应有多少来自"避开故障"、多少来自"更干净的上下文"，在这台机器上拆不开（vLLM 版本被驱动锁在 0.19.1）。反过来，如果只看分数，这个故障会被误读成"4B 能力不够，长对话就崩"。

## 5. 结果

**同一台原生口径推理服务、同一套采样，20 道测试题 × 4 遍**：

| | pass@1 | pass@4 | pass^4 | 截断率 | 刷屏对话 | 工具调用 / 客服轮 |
|---|---:|---:|---:|---:|---:|---:|
| 原始 prompt · 不思考（对照） | 0.750 | 0.900 | 0.550 | 18.8% | 25.0% | 0.44 |
| 精简 · 不思考 | 0.750 | 0.950 | 0.550 | 15.0% | 7.5% | 0.45 |
| **精简 · 思考（定版）** | **0.825** | 0.950 | **0.700** | **6.2%** | **0%** | 0.50 |
| DeepSeek-v4-Flash 自演客服 + 顾客 | 0.875 | 0.950 | 0.750 | 0% | 0% | 0.73 |

| 逐题配对 | Δpass@1 | Δ截断率 |
|---|---|---|
| 精简 · 不思考 − 对照 | +0.000 [−0.062, +0.075] | −3.8pp |
| **定版 − 对照** | +0.075 [−0.013, +0.175] | **−12.5pp [−22.5, −3.8]\*** |
| 定版 − 精简 · 不思考（思考的作用） | +0.075 [+0.000, +0.163] | |
| 定版 − DeepSeek 自演（全部 50 题） | −0.050 [−0.150, +0.055] | +8.0pp [+3.5, +13.5]\* |

**旧口径引擎上的 2×2（全部 50 题 × 4）** —— 用来分清是哪一项起作用：

| | 不思考 | 思考 |
|---|---:|---:|
| 原始 prompt | 0.630 | 0.650（+0.020） |
| 精简 | 0.640（+0.010） | **0.730（+0.100 [+0.020, +0.185]\*）** |

读法：
1. **单独精简不涨分**（两套引擎上都复现：+0.010 / +0.000）。上下文短了一半、刷屏少了一半、工具报错 10 → 2，但失败只是换了形态 —— 从"刷屏撞步"变成"比价算错、选错航班"。过程核查确认不是压缩丢了信息：精简版选错的航班和原模型在同一题上选错的是同一班，紧凑结果里正确那组的价格都在。
2. **单独开思考也几乎不涨**（+0.020）：原始 prompt 下开思考，刷屏对话仍有 18%、截断 17% —— 思考的产出被长度吃掉了。
3. **两项一起才显著**（+0.100\*）。[推断] 精简把长度压下来，思考才有空间改善判断。
4. 与 DeepSeek 的差距 pass@1 上不显著，**唯一显著落后的是截断率**（9% vs 1%，全部 50 题）；另外 DeepSeek 每个客服轮平均 0.73–0.96 个工具调用，4B 只有 0.5 —— 剩下的差距在"每轮产出密度"和写库题的判断上。

**口径说明**（一起报）：
- 同引擎下，定版对原始 · 不思考的 +0.075 在 20 题上**不显著**，显著的是截断率 −12.5pp。README 里的 "0.750 → 0.825" 是这组同引擎对照。
- 跨引擎的 "+0.095 [+0.030, +0.160]\*"（定版 vs 旧口径原始 prompt，50 题）也成立，但它包含了"换成官方原生调用方式"这一步，不是纯粹的外壳效应。
- DeepSeek 那行由同一个模型同时扮演客服和顾客，它对自己的顾客更容易"对上暗号"，这个参照偏高。
- 严格口径（再查 ACTION）下定版测试集是 0.713：全部 50 题上，开思考的配置约 8.5% 的对话"库和话都对、但 gold 动作参数没对上"（多写了冗余字段等），不思考的配置只有 0–2%。
